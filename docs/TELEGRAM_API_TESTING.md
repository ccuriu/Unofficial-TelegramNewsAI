# Telegram API: план дополнительного тестирования

Этот документ нужен для проверки поведения Unofficial TelegramNewsAI перед повторным открытием публичного репозитория.

## Зачем проводится тестирование

Telegram допускает сторонние MTProto/API-клиенты, но предупреждает, что аккаунты, входящие через неофициальные клиенты, автоматически находятся под дополнительным наблюдением. Точные критерии антиспам-системы и универсальные безопасные лимиты не публикуются.

До приостановки публичного распространения проект использовался в основном с подборкой примерно **35–50 каналов**. Это рабочий опыт, а не доказанный безопасный предел.

После перехода на 5.4.11 Testing первый контрольный прогон 19.09.2026 на существующей рабочей базе прошёл штатно: **31/31 канал**, обычный дайджест за 24 часа, без наблюдавшегося FloodWait, защитной остановки, RPC-ошибок или повторной авторизации. Один успешный прогон не доказывает безопасность режима.

Цель испытаний — увидеть реальные сигналы Telegram при обычном использовании, убедиться, что после признаков ограничения программа прекращает дальнейшую сетевую нагрузку, и описывать только **фактически протестированные сценарии**.

## Что изменено в 5.4.12 Testing

По сравнению с 5.4.11:

- `flood_sleep_threshold` Telethon принудительно равен `0`, поэтому короткий FloodWait не скрывается внутри библиотеки;
- первый обнаруженный `FloodWait` прекращает текущий сетевой этап без автоматического повтора;
- ошибки, похожие на `PEER_FLOOD`, отзыв/истечение сессии, бан номера, деактивацию или потерю авторизации, также вызывают защитную остановку вместо повторных запросов;
- обычный дайджест и backfill сначала восстанавливают сохранённые каналы из локального entity-cache Telethon через `get_input_entity`; полный `get_dialogs(limit=None)` остаётся только fallback при нехватке локального кэша или для пересоздания списка;
- если в уже настроенной установке исчез `telegram_session.session` или сохранённая сессия перестала быть авторизованной, программа не начинает новую авторизацию автоматически;
- запросы истории по-прежнему идут последовательно с явным `wait_time`;
- сохраняется межканальная пауза, увеличенная для больших списков;
- одновременный запуск двух обычных копий в одной Windows-сессии блокируется системным mutex;
- ML/embedding-поиск по собранному Telegram-контенту отключён; тематический поиск остаётся локальным через SQLite FTS5/LIKE;
- пользовательское название изменено на **Unofficial TelegramNewsAI** в соответствии с текущими Telegram API Terms.

Эти меры не являются способом обхода антиспам-системы и не гарантируют отсутствие ограничений.

## Правила испытаний

Не пытаться специально вызвать блокировку и не повышать нагрузку после ошибки или предупреждения Telegram. Не менять одновременно несколько параметров нагрузки: иначе нельзя понять, что повлияло на результат.

Не использовать несколько аккаунтов для обхода ограничений, чужие/официальные API credentials или эмуляцию официального клиента.

Не запускать несколько копий программы одновременно и не повторять тяжёлую операцию сразу только ради скорости теста.

Если доступ к аккаунту критичен, учитывать, что даже аккуратный тест не даёт гарантии отсутствия ограничений.

## Последовательность

### Этап 1 — текущий базовый режим

В течение 5–7 дней использовать существующий рабочий список:

- **31 канал**;
- обычный дайджест за 24 часа;
- естественная частота использования, без искусственных повторных прогонов;
- без массовой загрузки 90-дневной истории.

Цель: проверить поведение максимально близко к обычному использованию.

### Этап 2 — увеличение периода

Только после спокойного прохождения этапа 1, на том же списке каналов по одному разу проверить:

1. 7 дней;
2. 30 дней;
3. 90 дней — только после двух предыдущих.

Если локальная база уже содержит нужную историю, отдельно отметить, сколько данных реально пришлось получить из Telegram: сам выбор большого периода ещё не означает большую API-нагрузку.

### Этап 3 — увеличение числа каналов

Только если предыдущие этапы прошли без признаков ограничений:

1. вернуть/расширить список примерно до исторически использовавшихся 35–50 каналов;
2. около 60 каналов;
3. около 75 каналов;
4. около 100 каналов — только если предыдущий уровень прошёл стабильно.

Не увеличивать одновременно и число каналов, и глубину первой загрузки.

## Немедленная остановка теста

Тест прекращается и нагрузка не повышается, если произошло хотя бы одно из следующего:

- любой наблюдаемый `FloodWait`;
- защитная остановка Unofficial TelegramNewsAI;
- `PEER_FLOOD` или сходная ошибка ограничения;
- принудительный выход из Telegram-сессии;
- неожиданная необходимость повторной авторизации;
- ограничение действий аккаунта со стороны Telegram;
- необычная серия RPC-ошибок;
- уведомление Telegram о подозрительной активности;
- иное новое поведение аккаунта.

После такого события сначала анализируются журнал и обстоятельства. Сразу повторять ту же тяжёлую операцию нельзя.

## Что записывать после каждого запуска

Не сохранять номер телефона, API Hash, код подтверждения или содержимое приватных сообщений.

| № | Дата | Каналов | Период | Операция | База | Длительность | Просмотрено сообщений | FloodWait / RPC | Защитная остановка | Состояние аккаунта |
|---:|---|---:|---:|---|---|---:|---:|---|---|---|
| 1 | 19.09.2026 | 31 | 24 ч | обычный дайджест | существующая | — | 767 за период | не наблюдались | нет | без изменений |

Полезно сохранять соответствующий файл из `logs`, но перед любой будущей публикацией обязательно проверять его на личные данные.

## Как интерпретировать результат

Отсутствие блокировки в тестах не доказывает, что Telegram никогда не ограничит другой аккаунт в том же режиме. Корректная формулировка результата:

**«Этот сценарий был фактически протестирован на таких-то объёмах без наблюдавшихся ограничений на момент испытаний».**

## Отдельные блокеры публичного релиза

Даже успешные нагрузочные тесты API сами по себе больше не достаточны для открытия репозитория.

Перед публичным релизом также нужно закрыть два вопроса текущих правил Telegram:

1. **Content Licensing / AI-ML.** Программа уже не выполняет ML/embedding-обработку Telegram-контента и сама не отправляет JSON во внешние AI/ML-сервисы. Перед возвращением любого внешнего AI-сценария нужно отдельно подтвердить его допустимость по актуальным правилам.
2. **Sponsored Messages.** Telegram API Terms требуют поддержки официальных sponsored messages для сторонних приложений, предоставляющих доступ к содержимому каналов. Нужно определить применимость и корректную реализацию для локального пакетного коллектора без обычного интерфейса канала; не добавлять лишние API-запросы или рекламу «наугад».

Пока эти вопросы не закрыты, проект остаётся приватным независимо от результатов теста нагрузки.
