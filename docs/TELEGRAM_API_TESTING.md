# Telegram API: план дополнительного тестирования

Этот документ нужен для проверки поведения TelegramNewsAI под разной нагрузкой перед повторным открытием публичного репозитория.

## Зачем проводится тестирование

Telegram допускает сторонние MTProto/API-клиенты, но прямо предупреждает, что аккаунты, входящие через неофициальные клиенты, автоматически находятся под дополнительным наблюдением. Точные критерии антиспам-системы и универсальные безопасные лимиты не публикуются.

До приостановки публичного распространения TelegramNewsAI использовался в основном с подборкой примерно **35–50 каналов**. Это рабочий опыт, а не доказанный безопасный предел.

Цель испытаний — проверить, как программа ведёт себя при росте числа каналов и глубины истории, увидеть реальные `FloodWait` и другие RPC-ошибки, убедиться, что после признаков ограничения программа останавливает дальнейшую сетевую нагрузку, и определить только **протестированные режимы**, не объявляя их гарантированно безопасными.

## Что уже изменено в 5.4.11 Testing

- запросы истории выполняются с явным `wait_time` между последовательными `GetHistoryRequest`;
- между каналами добавлена небольшая пауза;
- для списков больше 50 каналов межканальная пауза автоматически увеличивается;
- к явному `FloodWait` добавляется небольшой запас времени перед повтором;
- если `FloodWait` превышает допустимый для автоматического ожидания порог или повторяется до исчерпания попыток, текущая синхронизация останавливается и остальные каналы не запрашиваются;
- если защитная остановка произошла на обычной синхронизации перед поиском, догрузка старой истории в том же запуске не начинается;
- в журнал записываются параметры защитного профиля, длительность синхронизации, количество обработанных каналов и факт защитной остановки;
- при первой авторизации пользователь должен явно подтвердить, что увидел предупреждение о риске ограничений.

Эти меры снижают резкие пики обращений к API, но не являются способом обхода антиспам-системы и не гарантируют отсутствие ограничений.

## Правила испытаний

Не повышать нагрузку после ошибки или предупреждения Telegram. Не пытаться специально вызвать блокировку. Не менять одновременно несколько параметров: иначе нельзя будет понять, что именно повлияло на результат.

Для нагрузочных испытаний лучше использовать аккаунт, потеря доступа к которому не критична. Новый или VoIP-номер не считать автоматически более безопасным. Основной аккаунт не использовать для агрессивного стресс-теста.

Перед каждым этапом убедиться, что предыдущий прошёл без необычных ограничений. Между тяжёлыми первичными загрузками не запускать несколько копий программы и не повторять операцию сразу только ради ускорения.

## Последовательность

### Этап 1 — базовый режим

7 дней обычного использования:

- 35–50 каналов;
- обычный дайджест за 24 часа;
- не более нескольких запусков в сутки;
- без повторной массовой загрузки 90-дневной истории.

Цель: подтвердить, что после добавления защитных пауз привычный режим остаётся стабильным.

### Этап 2 — увеличение периода

На том же списке каналов по одному разу проверить:

1. 7 дней;
2. 30 дней;
3. 90 дней — только после спокойного прохождения предыдущих этапов.

Если локальная база уже содержит нужную историю, это не считается нагрузочным испытанием: важно отдельно отметить, сколько данных реально пришлось получить из Telegram.

### Этап 3 — увеличение числа каналов

Только если предыдущие этапы прошли без признаков ограничений:

1. около 60 каналов;
2. около 75 каналов;
3. около 100 каналов — только если 75 прошли стабильно.

Не перескакивать сразу с 35–50 на 100+.

## Немедленная остановка теста

Тест прекращается и нагрузка не повышается, если произошло хотя бы одно из следующего:

- длинный или повторяющийся `FloodWait`;
- защитная остановка TelegramNewsAI;
- принудительный выход из Telegram-сессии;
- неожиданная необходимость повторной авторизации;
- ограничение действий аккаунта со стороны Telegram;
- необычная серия RPC-ошибок;
- уведомление Telegram о подозрительной активности;
- иное поведение аккаунта, которого до теста не было.

После такого события сначала анализируются журнал и обстоятельства. Повторять ту же тяжёлую операцию сразу нельзя.

## Что записывать после каждого запуска

Не сохранять номер телефона, API Hash, код подтверждения или содержимое приватных сообщений.

| Дата | Каналов | Период | Операция | Новая/существующая база | Длительность | Сообщений просмотрено | FloodWait / RPC ошибки | Защитная остановка | Состояние аккаунта |
|---|---:|---:|---|---|---:|---:|---|---|---|
| | | | | | | | | | |

Полезно сохранять соответствующий файл из `logs`, но перед публикацией когда-либо в будущем обязательно проверять его на личные данные.

## Как интерпретировать результат

Отсутствие блокировки в тестах не доказывает, что Telegram никогда не ограничит другой аккаунт в том же режиме. Результат позволяет утверждать только:

**«Этот сценарий был фактически протестирован на таких-то объёмах без наблюдавшихся ограничений на момент испытаний».**

Повторное публичное открытие проекта имеет смысл только после того, как базовый режим стабильно проходит испытания, защитная остановка работает как задумано, а README ясно отделяет протестированные режимы от неизвестных лимитов Telegram.
